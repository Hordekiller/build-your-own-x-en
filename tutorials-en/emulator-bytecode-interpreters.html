Home-grown bytecode interpreters

About

From Bumble's engineering blog: the design evolution of a bytecode interpreter — a VM that grows from a single accumulator, through a stack machine, to registers — exactly the way production VMs are born.

What you'll learn

  • Why bytecode beats direct interpretation for speed and portability
  • The three classic VM shapes: accumulator, stack, register
  • Designing instruction sets that decode efficiently
  • How a modern engine (like V8 or JVM) descends from these choices

Core idea

The first interpreter is almost rude in its simplicity — a program counter and one accumulator:

cuint8_t *ip;
uint64_t accumulator;
} vm;
typedef enum {
	/* increment the register */
	OP_INC,
	/* decrement the register */
	OP_DEC,
	/* add an immediate argument to the register */
	OP_ADDI,
	/* subtract an immediate argument from the register */
	OP_SUB
} Opcode;
c#define STACK_MAX 256
struct {
	uint8_t *ip;
	/* fixed-size stack */
	uint64_t stack[STACK_MAX];
	uint64_t *stack_top;
	/* a single register that holds the result */
	uint64_t result;
} vm;
c#define REGISTER_NUM 16
struct {
	uint16_t *ip;
	uint64_t reg[REGISTER_NUM];
	uint64_t result;
} vm;
typedef enum {
	/* load an immediate value into rX */
	OP_LDIMM
} Opcode;

Why it matters

Reading the actual progression — accumulator to stack to registers — explains why JavaScript engines, Python and the JVM look the way they do today.
